PFO 2 — Sistema de Gestión de Tareas

Aplicación cliente-servidor con API REST en Flask, protección de contraseñas mediante hashing y persistencia relacional en SQLite.

🎯 Objetivos Cumplidos

  • API REST con Flask: Endpoints funcionales para registro, login, gestión y consulta de tareas.
  • Protección Criptográfica: Hashing irreversible de contraseñas utilizando el módulo werkzeug.security.
  • Persistencia SQLite: Base de datos relacional local tareas.db con integridad referencial.
  • Cliente de Consola Interactivo: Menú completo para interactuar con la API REST vía HTTP.
  • Pantalla de Bienvenida HTML: Endpoint GET /tareas renderizando un panel visual de bienvenida para navegadores.

🏗️ Arquitectura del Sistema

Cliente de Consola (Python)

Consume la API REST a través de requests.Session, conservando las cookies de autenticación de forma transparente.

python cliente.py

Servidor API REST (Flask + SQLite)

Valida credenciales con hashes criptográficos, maneja sesiones y persiste los datos en tareas.db.

python servidor.py

🌐 Endpoints de la API REST

Método Ruta Autenticación Descripción
POST /registro No requerida Recibe usuario y contraseña, hashea la clave y persiste en SQLite.
POST /login No requerida Valida credenciales contra el hash almacenado y crea la sesión autenticada.
GET /tareas Requerida Muestra el HTML de bienvenida en navegador o retorna array JSON de tareas para clientes API.
POST /tareas Requerida Crea una nueva tarea asociada al usuario con estado inicial pendiente.
PUT /tareas/<id>/cerrar Requerida Modifica el estado de la tarea a cerrada validando pertenencia del usuario (403 si es ajena).
POST /logout Requerida Invalida la sesión activa e impide posteriores accesos a las tareas.

💡 Respuestas Conceptuales

1. ¿Por qué hashear contraseñas?

Almacenar contraseñas en texto plano constituye una falla crítica de seguridad. Si la base de datos se ve comprometida o filtrada, cualquier atacante tendría acceso inmediato a las credenciales. El hashing criptográfico proporciona:

  • Irreversibilidad (Unidireccionalidad): Es una función matemática de un solo sentido; a partir del hash no es posible reconstruir la clave original.
  • Salting Aleatorio: Algoritmos como los implementados en werkzeug.security añaden un salt único para cada usuario, evitando ataques por tablas arcoíris (rainbow tables) y garantizando que dos claves idénticas generen hashes completamente distintos.
  • Protección contra Fuerza Bruta: El algoritmo introduce un costo computacional deliberado para ralentizar intentos masivos de adivinación.

2. Ventajas de usar SQLite en este proyecto

  • Serverless (Sin demonio independiente): No requiere instalar ni ejecutar servicios en segundo plano (como MySQL o PostgreSQL); el motor se ejecuta directamente embebido en el proceso de Python.
  • Cero Configuración: No requiere gestión de usuarios del SGBD, configuración de puertos de escucha ni esquemas complejos.
  • Portabilidad Absoluta: Toda la base de datos reside en un único archivo físico (tareas.db), facilitando copias de seguridad, pruebas y evaluaciones locales.
  • Transaccionalidad ACID: Brinda soporte completo para transacciones atómicas, consistentes, aisladas y duraderas mediante el módulo estándar sqlite3.
